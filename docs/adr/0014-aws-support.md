# ADR 0014: AWS support, mock first, with keyless per-organization access

- Status: Accepted. P1b implements AWS in mock mode only. Real AWS work runs in its own track
  (A1–A4 in the [implementation plan](../implementation-plan.md)).
- Date: 2026-09-27
- Related: [ADR 0003](0003-customer-access-per-organization-identities.md) (GCP access),
  [ADR 0005](0005-terraform-only-writer-state-and-secrets.md), [ADR 0013](0013-environments-and-registered-networks.md)

## Context

The v2 review limited the initial implementation to GCP. On 2026-09-27 the product owner asked
for GCP and AWS now, with Azure later. The rules that shaped GCP still apply:

- Terraform is the only writer.
- There are no long-lived keys.
- One organization must never reach another organization's cloud.
- The core must not be coupled to one cloud.
- No real customer infrastructure is touched before the phases that allow it.

## Decision

### Same interface, mock first

- AWS implements the existing `CloudProvider` interface:
  - account validation;
  - region, zone, instance-type and storage catalogs;
  - network lookup (ADR 0013);
  - Terraform plan, apply and destroy;
  - read-only status and node reports.

  The domain, workflows, API and console do not branch on the provider.
- P1b ships a simulated AWS provider only. It uses the same simulated data plane as GCP, so a
  cluster on AWS boots, reports health and metrics, and can have faults injected, scaled and
  deleted.
- There is no AWS SDK, credential or Terraform AWS module yet. When real mode is enabled (GCP in
  P4), AWS stays unavailable until its own track delivers it. Azure is shown in the console as
  not yet available and is rejected by the API.

### Customer access: assume a role, keyless and per organization

```text
Terraform job for one operation (GKE, organization's Kubernetes ServiceAccount)
    │ Workload Identity → Google identity org-<org-key>-tf (ADR 0003)
    │ AssumeRoleWithWebIdentity (Google-signed ID token; trust condition on the identity's unique ID)
    ▼
Platform AWS account: role byoc-org-<org-key>          one per organization, may only call sts:AssumeRole
    │ sts:AssumeRole with ExternalId = the organization's external ID
    ▼
Customer AWS account: role db-platform-provisioner      least-privilege policy, created by the customer
```

- The customer creates the provisioner role. Its trust policy allows only their organization's
  platform role, with the condition `sts:ExternalId` equal to the organization's external ID.
- The **external ID** is generated by the platform once per organization (`byoc-` followed by 32
  hex characters). It is shown in the console and never chosen by the customer. It stops the
  confused deputy even if a customer trusts the whole platform account instead of their
  organization's role.
- **Proof of ownership**, as in ADR 0003:
  - the role ARN must be in the registered AWS account;
  - an account becomes `CONNECTED` only after the organization's platform role assumes the
    customer role with that organization's external ID.

  Organization A registering B's role fails, because B's trust policy names B's principal and
  B's external ID. Failed assumptions return one uniform message.
- No access keys exist anywhere. Monitoring and network lookups use a separate read-only role
  (`db-platform-monitor`), assumed the same way from the organization's read identity.
- A cloud account stores the provider, the AWS account ID (in the same field as a GCP project ID),
  the default region and the role ARN. The API accepts `service_account_email` only for GCP and
  `role_arn` only for AWS.

### Validation (real mode, AWS track)

1. `sts:AssumeRole` with the external ID (consent).
2. `sts:GetCallerIdentity` returns the registered account.
3. The region is enabled (`ec2:DescribeRegions`).
4. The required actions are allowed: EC2 `DryRun` calls for launching instances, creating volumes
   and security groups, plus `iam:SimulatePrincipalPolicy` for the rest. Missing actions are
   listed.

### Data plane on AWS (AWS track)

| Concern | AWS |
|---|---|
| Network | Registered VPC and subnets (ADR 0013); one security group per cluster allowing 9200 and 9300 from the subnet ranges |
| Compute | EC2 instances without public IPs, IMDSv2 required; `m6i`/`r6i` (x86_64) and `m7g`/`r7g` (Graviton, arm64) families |
| Storage | One encrypted EBS `gp3` volume per node, not deleted on instance termination |
| Secrets | AWS Secrets Manager, readable only by the cluster's instance profile |
| Artifacts | Private S3 bucket per cluster for the agent binary |
| Identity | Instance profile per cluster; the agent proves its identity with the signed EC2 instance identity document |
| Node reports | Agent heartbeat (ADR 0007); a cloud-side report channel equivalent to GCE guest attributes is decided in A4 |
| State | Terraform state in the platform's GCS state bucket, per organization and cluster, as for GCP (ADR 0005) |

HA follows ADR 0011 and ADR 0013: three master-eligible nodes in three availability zones.

## Alternatives rejected

- **IAM user access keys from the customer**: long-lived secrets, the same objection as
  service-account keys (TRD §43).
- **One platform role trusted by every customer**: one credential reaching every customer (the
  objection of ADR 0003). The external ID alone does not fix that.
- **Customer-chosen external IDs**: a customer could reuse another organization's ID. The platform
  generates them.

## Consequences

- The platform needs its own AWS account, with one IAM role per organization and an OIDC trust to
  Google. Offboarding deletes the organization's role, which makes the customer's grant inert.
- The console shows each organization's external ID and a trust-policy template.
- Every AWS feature beyond mock mode is new work in the AWS track:
  - validation and network lookup;
  - the Terraform modules;
  - the report channel;
  - an end-to-end run against a sandbox account.
